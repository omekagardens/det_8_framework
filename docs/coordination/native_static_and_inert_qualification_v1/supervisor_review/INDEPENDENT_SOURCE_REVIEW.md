## F01 — an ordinary pump error stops the healthy sibling stream

**Locations:** supervise_native.py 348–371, outer catch 374–375 and pipe close 414–419; the analogous process-observer paths are 150–177 and 198–209.

The outer per-stream handler catches only BlockingIOError. An ordinary read, output write, selector unregister or pipe close exception therefore exits the entire main pump. Finalization performs process observation/cleanup and then closes every surviving pipe without another drain. A concrete source-level path is a stdout write raising an ordinary OSError while stderr already has pending diagnostic bytes: the healthy stderr descriptor remains registered, but control leaves the loop and subsequently closes it. The original 315-second deadline can still have ample time. No inability to read stderr has been established, yet its queued bytes are discarded.

The completion honestly fails (its stderr EOF flag remains false); the problem is loss of independent complementary failure evidence, not false positive acceptance. Fsync/close/readback of the zero-or-short retained sibling file does not recover bytes that were left in the pipe. This is weaker than the unchanged native caller's explicit per-stream ordinary exception handling at caller.py 699–717, which records the failing pump, attempts its own unregister/close and retains the other pump independently.

The new ps observer has the same ordinary-failure structure: an exception while reading or registering one stream reaches 176–177, followed by closure of all registered streams in 198–209. It cannot substantiate the docstring's unqualified “complete raw streams retained even on ordinary failure” for the healthy sibling. On partial observer registration, cleanup also enumerates registered keys rather than every successfully acquired Popen pipe. This remains a failed observation, but raw evidence and acquired-handle cleanup need explicit independent handling.

**Required repair:** isolate each ordinary pump failure, preserve the earliest error, safely disable the failed pump and continue servicing the healthy pump within the existing deadline/caps while termination proceeds. Independently attempt unregister/close for acquired handles; distinguish registration state from handle ownership. Do not retry the whole operation, pretend EOF, overwrite partials, change limits or promise recovery after hard abort/kernel stall. Apply the same principle to the bounded ps helper where it claims ordinary two-stream retention.

**Required focused coverage:** extend existing S04/S05/S10 rather than introduce a new harness. Exercise both stdout and stderr read/write failures with the sibling already readable; include short partial output writes and unregister/close failures, plus partial observer registration. Verify exact retained healthy-stream bytes/EOF or an independently recorded real boundary failure, earliest error preservation, all available final checks and unchanged deadlines/caps. These cases are not covered by successful cap handling or late fsync/readback doubles alone. No such case was executed here.

## F02 — direct fallback kill has no independent bounded reap

**Locations:** supervise_native.py 380–411, especially observer failure break 401–403 and direct kill 406–411; final failed-reap handling 459–480.

If an ordinary process observer or journal error aborts the cleanup observation, the code breaks the cleanup loop. It then correctly attempts `process.kill()` on the still-owned direct child. There is no subsequent bounded `process.poll()`/waitpid attempt, even when almost all the original 315-second budget remains. Source-level example: the first observer call fails quickly, the cleanup observer fails quickly, the caller is still running, and the fallback kill returns. The code proceeds immediately to closing pipes, data-file tails and a FAILED completion whose `caller_reaped` remains false.

Sending the signal is not reaping. Popen's implementation may internally poll before signaling or opportunistically reap later during destruction; neither supplies the required explicit bounded post-kill observation and saved actual return/reap state. A missing/failed ps or journal is not a reason to abandon the independent owned-child wait mechanism. Descendant discovery and complete group cleanup may remain unavailable; those are separate facts.

The source and contract accurately deny cleanup credit on this route. That candor must remain, but it does not replace an available ordinary direct-child reap attempt. The requested ordinary supervision should not require external recovery solely because its own observer recording failed while a valid direct-child handle and time budget remain.

**Required repair:** after an ordinary fallback kill, attempt genuine nonblocking direct-child reap within the original deadline, independently of ps/journal success, and record actual code/reap or explicit bounded failure. Preserve the first observer/journal error, never infer descendant absence from direct-child exit, never signal unknown/stale descendant IDs, and grant no extra cleanup time. Hard abort remains the deliberately weaker nonblocking kill/partial-evidence route; this finding does not require polling through a hard abort.

**Required focused coverage:** add distinct early observer failure and journal-write failure while the direct caller is alive, followed by ordinary successful kill/reap; also kill failure, delayed nonreap until the unchanged deadline and already-exited direct child. Verify the actual poll/wait event and retained return/reap state without granting group/qualification credit. Existing S05/S10/S13 can carry these finite cases. Signals-sent markers or garbage-collection behavior are not the oracle.
